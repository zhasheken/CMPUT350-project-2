CMPUT350 Project 2: ECS Platformer
==================================

Engine implementation notes
---------------------------

EntityManager stores entities in a vector and reuses removed entity IDs from a
free list. Each entity has a component-index table; kNullComponent means that
the entity does not have that component type. ComponentStorage keeps logical
slots in vectors, tracks live slots and owners separately, and reuses freed
slots instead of compacting storage. A vector reallocation can invalidate
component references; entity IDs can identify a different entity after reuse.

CollisionComponent.collisionBox is relative to LocationComponent.loc.
CollisionLateSystem records the translated world-space box before movement;
CollisionSystem compares it with the post-movement box to resolve contacts.

SoundManager uses one map for sf::SoundBuffer ownership and a second map for
sf::Sound objects that refer to those buffers. SpriteManager caches textures
by path and stores sf::Sprite objects in a deque, so adding sprites preserves
references to existing sprites. Registering the same texture path again
reuses its texture but returns a new sprite ID.

Gameplay implementation notes
-----------------------------

Movement and gravity are per update values. Current input tuning is run speed
7, jump velocity 18, dash velocity 40, ground/air acceleration 4/3, and a dash
cooldown of 60 updates.

Wall jumps use coyote time: a wall jump is still allowed for 6 updates after
leaving a wall.

When left and right are both held, the most recently pressed arrow wins.

Dashing while falling cancels downward velocity.

Stars are dynamic entities without InputComponent. SpawnSystem gives them a
small random upward launch (5 pixels per update) and downward
GravityComponent; CollisionSystem handles star bounces, collisions between stars,
and deferred collection/removal. Star bounces use 0.7 restitution and settle
when reflected speed is below 1 pixel per update.

The map loader loads sky.map before world.map so background sprites are added
first.

System access and update order
------------------------------

Systems take EngineView rather than ECSEngine and obtain managers through its
manager getters. The systems in main.cpp are registered and run in this order:

1. CollisionLateSystem snapshots collision boxes before anything moves.
2. InputSystem updates player movement intent.
3. GravitySystem applies acceleration and fall limits.
4. MovementSystem changes entity locations.
5. CollisionSystem resolves obstacles, handles stars, and collects stars.
6. ScoreSystem updates the score display after collection.
7. CameraSystem follows the player and applies camera shake.
8. SpriteSystem draws world space and screen space sprites.
9. SpawnSystem counts down spawners and creates stars for the next update.

Boxes are saved before anything moves and resolved after movement. Spawning
runs last, so new stars appear on the next frame. SystemManager runs systems
in the order they were added and stops if one returns kExit.

ECSEngine snapshots keydown into lastKeydown at the start of each frame, then
polls events and updates keydown on every InputComponent. Losing window focus
clears held key state. D toggles collision debug drawing, P pauses/resumes, and
N advances one frame while paused.

AI assistance disclosure
------------------------

AI assistance was used to implement or refine player input, collision, understadning of 
camera following and shake, Focused tests for those behaviors were also AI-assisted. 

Prompt: “The wall jump feels weird because it pushes me away from the wall before I press anything and its hard to jump off. Help me implement coyote time, please give me a simple step by step.”
Reflection: This was successful because not having coyote time made wall jumps difficult. The code was short and easy to follow. 
One downside was that wall jumps could go further, so we had to retune the movement so the second set of spikes still needs a dash
but this helped guide the movement in the right direction.

Prompt: “Walk me through implementing the component storage and entity manager parts of the engine step by step, in a simple beginner-friendly style that follows the spec as follows [pasted spec]”
Reflection: This helped me understand how entities, component storage and the index table fit together, and how to add, remove and look up components.

Prompt: “Help me finish the engine loop: processing SFML events into the input component, running the systems, and drawing debug collision boxes.”
Reflection: This helped me understand how key presses get into the input component and how the debug, pause and step keys work. The first version used things I didn’t understand but further chats simplified the loop into steps I could understand much better.

Build and run
-------------

From the repository root:

    cmake -S . -B build
    cmake --build build --parallel
    ctest --test-dir build --output-on-failure
    (cd build/platformer && ./platformer)

The project uses C++20 and enables -Wall, -Wextra, and -Wpedantic. A successful
local build does not replace the required lab-machine build and gameplay test.
